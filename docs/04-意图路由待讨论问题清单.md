## 一、数据飞轮：离线评测与反馈闭环（建议优先讨论）

意图路由本质是检索 + 分类系统，但目前只有在线 metric、没有离线评测与反馈回流——embedding 模型、阈值、prompt 的每次改动都无法离线判断好坏。

### 1. 离线 golden set 缺失【有方向】

- 现状：测试全部用 stub chat + 哈希向量 fake embedding（`stub_llm.py:_stub_embedding`），测的是"机制"（mock 返回 X 断言行为 Y），测不出"这句话语义上该路由到哪个 Skill"。
- 方向：`tests/routing/golden/` 放 30~50 条人工标注 YAML（message → 期望命中工具/路径），用**录制的真实 embedding 响应快照**跑 pytest（不依赖外部服务、又有真实语义），产出召回/误杀报告；换 embedding、调阈值、改 prompt 前后对比。
- 业界对标：BFCL、ToolBench/ToolEval（大规模版）；小团队 30~50 条高频 + 易错 query 即可起步。

### 2. 用户侧反馈信号未采集【待讨论】

- 现状：误杀 metric（change D7）只统计"模型调用了推荐集外工具"；但更早暴露误杀的信号——用户重复提问、换说法重问、澄清后仍无工具、"不对/不是这个"——完全没有采集。
- 方向：澄清后 N 轮内重复澄清、短时间同义改写重发等启发式信号入 metric/日志。

### 3. 阈值校准流程未定义【待讨论】

- 现状：D8 给了分数分布 histogram（原料），但 `score_threshold=0.5`、`margin=0.1`、`floor=threshold*0.5` 仍是拍脑袋值；谁看数据、多久调、按什么标准调，没有流程。
- 依赖：问题 1（golden set）先行。

### 4. 测试替身不保真语义【待讨论】

- 与问题 1 同源：stub 哈希向量"共享 token 即相似"，路由单测的语义断言没有可信度。golden set + 响应快照可解。

## 二、路由机制

### 5. 规则命中即终判、无置信校验【有方向】

- 现状：`rules.py:27` 第一条正则命中直接返回 PATH_RULE，不走向量/LLM。
- 风险："帮我看看退款按钮为啥点不了"命中退款关键词 → 强制收窄退款工具，连兜底机会都没有。规则是逃生门也是误杀门（D7 误杀计数覆盖 rule 路径，可观测但不拦截）。
- 方向：规则命中再过一次向量分数校验，规则目标与向量 top1 完全不沾边时降级为"规则建议"交 LLM 裁决——牺牲部分确定性，需权衡。

### 6. 放行集无"最少工具数"下限【待讨论】

- 现状：`router.py:101` 的 `floor=threshold*0.5` 是未校准系数；vector 高置信放行可能只有 1 个工具，收窄太狠 = 误杀面大，无最低放行数保障。

### 7. 无 category 的 Skill 在兜底路径不可达【待讨论】

- 现状：`_classify` 只在 categories 列表中选择（`router.py:111`），category 为空的 Skill 只能靠向量/规则命中，LLM 兜底永远选不到它。

### 8. chitchat 误判无二次确认【待讨论】

- 现状：LLM 判 chitchat 即空工具纯对话（`router.py:126`），误判时用户拿不到工具回答，无任何补救。

### 9. 多意图/复合请求无显式处理【待讨论】

- 现状："查订单 123 到哪了，顺便把退款办了"靠 top-k 工具集隐式覆盖，无意图分解/planner。

### 10. 轮中动态再检索（元工具 search_tools）缺失【Non-Goal 待数据】

- 现状：路由是建 Agent 前的一锤子买卖，整轮 ReAct 看不到被误杀的工具，模型只能徒手作答。
- 方向：给模型一个 `search_tools` 元工具，轮中按需再检索加载（Claude Agent Skills 渐进式披露、MCP 工具搜索方向）。代价：多一跳延迟/token，LangGraph 静态工具集需手搓"轮中增工具"。
- 触发：误杀率数据证明静态收窄不够时再议（D7 metric 为此铺路）。

### 11. supervisor 多子代理 / handoff【Non-Goal 待数据】

- 现状：LLM 选 category 收窄是 supervisor 的静态廉价版——路由 LLM 干了调度的活，但发生在建 Agent 前、子代理无独立 prompt、不能 handoff 回来。
- 方向：LangGraph supervisor / OpenAI Swarm handoff / AutoGen GroupChat，解决域间 prompt 稀释与子代理独立演进；代价是架构复杂度、跨代理状态传递、handoff 死循环、token 翻倍。同样待误杀/兜底率数据。

### 12. 兜底 LLM JSON 解析失败无独立计数【有方向】

- 现状：`_parse_json` 失败返回 `{}`（`router.py:152`）→ 走澄清；解析失败（prompt 不稳）与真低置信混成一个 clarify 率，调 prompt 时无信号。
- 方向：details/metric 区分 `parse_failed`。

### 13. 路由 LLM 无独立短超时【有方向】

- 现状：兜底/改写 LLM 复用执行模型超时（60s）；低置信轮最坏多等 60s 才澄清。分类/改写是短任务，应配独立短超时（如 10s）。

### 14. 路由 LLM 与执行 LLM 同模型【待讨论】

- 现状：`app.state.model` 同时用于执行与路由分类/改写；分类可用更便宜的小模型降延迟/成本（需独立配置项）。

## 三、工程与运行

### 15. 索引启动阻塞、无热更新【有方向】

- 现状：索引仅在 lifespan 启动构建（`app.py:90`）；缓存失效时千级文本分批 embed 可能数十秒；运行时注册新 Skill 不进索引。
- 方向：后台构建 + 就绪前规则路/BM25 顶上；插件热加载/灰度场景需索引增量更新。

### 16. 同步 CPU 计算阻塞 event loop【待讨论】

- 现状：`index.search` / BM25 是纯 Python 同步计算，而 `route()` 是 async；千级向量 × 256 维 + BM25 在高并发下阻塞 loop。当前规模风险中低，必要时 offload 线程池。

### 17. 索引缓存多实例写竞争【待讨论】

- 现状：`.skill_index_cache/skill_index.json` 直接写（`index.py:130`），多实例同时启动可能互踩；写临时文件 + rename 可解。当前单实例部署约束，低优。

### 18. examples 质量治理只做了一半【待讨论】

- 现状：`has_examples=false` 解决"有没有"，但 examples 写得差（缺口语变体/反例）无反馈机制；方向是 bad case 回灌 + examples 版本化，依赖数据飞轮（问题 1/2）。

### 19. 澄清选项数量上限【已定：IRCQ D11】

- 现状：`_default_clarify` 列出全部候选 categories（`router.py:169`），数十个域时澄清文案列一长串。
- 决策（已并入进行中 change `intent-routing-context-quality` 的 D11）：结构化澄清选项数量上限 `routing.clarify_option_max`（默认 4），候选来自 LLM 兜底 category/点名 Skill 与向量+BM25 融合 top-N；超出不入选，用户仍可手打走文本闭环。
