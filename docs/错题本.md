# 错题本（general-agent 迁移）

记录从 seederive-agent 迁移/通用化过程中遇到的问题、根因与修复。

## E1. langchain-core 1.x：`AIMessageChunk(tool_call_chunks=None)` 报 ValidationError

- **现象**：OpenAI SSE 适配层在收到纯文本 delta（无 tool_calls）分片时抛
  `pydantic_core.ValidationError: tool_call_chunks Input should be a valid list [input_value=None]`，
  导致整个 turn 以 `error` 事件失败。
- **根因**：旧代码（langchain-core 0.3 时代）用 `tool_call_chunks=... or None` 表示"无工具调用分片"；
  langchain-core 1.x 该字段类型为 `list[...]`，不接受 `None`，必须传空列表 `[]`。
- **修复**：`general_agent/llm.py` `_emit_chunk` 中 `AIMessageChunk(content=..., tool_call_chunks=tool_call_chunks)`，
  `tool_call_chunks` 始终为 list（无工具分片时为 `[]`）。
- **教训**：大版本依赖升级（langchain-core 0.3 -> 1.x、langgraph 0.2 -> 1.x）后，pydantic 模型字段的
  "Optional vs 空容器"语义可能收紧；迁移后必须跑端到端流式用例，不能只靠非流式/单测。

## E2. 批量字符串替换造成路径"双重替换"

- **现象**：文档中 LLM 端点被替换成 `/v1/chat/completions/completions`。
- **根因**：机械替换 map 中先把 `/v1/chat/stream` -> `/v1/chat/completions`，再把 `/v1/chat` -> `/v1/chat/completions`，
  后者匹配到了前者产物的前缀，造成叠加。
- **修复**：替换后全局 grep 产物特征串（`completions/completions`）检测并回改；批量替换后必须做残留/叠加扫描。

## E3. uv 构建本项目被 Windows 应用控制策略拦截（os error 4551）

- **现象**：`uv sync` 在"Building general-agent"（hatchling 构建本机包）时报
  `应用程序控制策略已阻止此文件 (os error 4551)`，临时构建目录的 python 被策略阻止。
- **根因**：本机安全策略阻止 uv 在缓存构建目录里运行解释器构建本机项目；第三方 wheel 安装不受影响。
- **修复/绕行**：`uv sync --no-install-project` 只装依赖到 `.venv`，运行/测试时用 `PYTHONPATH=.` 指向源码目录
  （`$env:PYTHONPATH="."; .venv\Scripts\python -m pytest`）。不影响代码，纯环境约束。

## E4. TestClient 无法读取无限 SSE 流（既有经验，迁移时复验）

- **现象**：`GET /stream` 是无限 SSE，FastAPI TestClient/ASGITransport 会 `await` app 完成才返回 response.start，
  用 TestClient 读会一直挂起（表现为 pytest 超时）。
- **处理**：沿用原方案——`GET /stream` 的 e2e 用后台线程跑真实 uvicorn（随机空闲端口）+ httpx 验证
  replay/心跳/notification；`POST /chat` 为有界流，可用 TestClient。见 `tests/conftest.py::run_server`。

## E5. aiomysql 单条 execute 不支持多语句 DDL

- **现象**：`mysql_client.init_schema` 原本一次 `cur.execute(SCHEMA_DDL)` 建 `agent_message`；新增
  `agent_user`/`agent_chat_session` 三张表用 `;` 拼成一条字符串后执行，多语句不被 aiomysql 默认接受。
- **根因**：aiomysql（底层 PyMySQL）默认 `CLIENT.MULTI_STATEMENTS` 未开启，一次 execute 只能跑一条 SQL。
- **修复**：`SCHEMA_DDL.split(";")` 后逐条 `execute`（strip 掉空段）。

## E6. tests 目录无 `__init__.py`，测试模块间不能用相对导入

- **现象**：`tests/test_auth_web.py` 写 `from .conftest import ...` 报
  `ImportError: attempted relative import with no known parent package`。
- **根因**：pytest 用 rootdir 插入 sys.path 的模式收集，tests 不是包；既有测试均用 `from conftest import ...`。
- **修复**：统一改为 `from conftest import build_test_app, parse_sse`。

## E7. max_tool_rounds 中断遗留无 ToolMessage 的 tool_calls，污染历史致会话永久 400

- **现象**：模型连续请求工具调用、达到 `recursion_limit` 时抛 `GraphRecursionError`；此时最后一条
  `AIMessage(tool_calls=[...])` 已经 `on_chat_model_end` 捕获，但工具尚未执行（无对应 ToolMessage）。
  该条仍被 `append_messages` 落库。下一轮 `load_messages` 重建后发给 OpenAI，出现
  "assistant(tool_calls) 后直接跟 human"，OpenAI 返回 400；`_trim_history` 只防开头孤儿 ToolMessage，
  不防末尾未应答 tool_calls，故**该会话之后每轮都报错**，直到历史自然老化。
- **根因**：工具调用配对（assistant.tool_calls ↔ tool message）在"轮次异常中断"时没有兜底清洗。
- **修复**：`runner.py` 新增 `_drop_unanswered_tool_calls`——按现有 ToolMessage 的 tool_call_id
  集合过滤 AIMessage.tool_calls；清洗后既无内容也无工具调用的空 AIMessage 直接丢弃。
  在两处应用：① 载入历史后（修复已污染的旧数据）；② 持久化前（不再写入新污染）。
- **教训**：任何"工具协议消息成对出现"的假设，都要考虑轮次中途异常（递归上限/错误/取消）的收尾；
  落库前清洗 + 读取时清洗双保险，避免脏数据固化。

## E8. `auth_mode=jwt` 占位分支静默放行（fails open）

- **现象**：`security._check_auth` 对预留的 jwt 模式直接 `return`，运维若误配 `auth_mode: jwt`
  会以为有鉴权，实际 `/chat`、`/stream` 全部未授权可访问。
- **修复**：占位/未实现的鉴权模式改为抛 `GovernanceError(500, "CONFIG", ...)`，宁失败勿放行。
- **教训**：安全相关的"预留分支"默认必须拒绝（fail closed），不能默认允许。

## E9. 对话中途"停止"后重叠轮次导致历史交错 + 孤儿会话 + 前端假状态

- **现象**：前端点"停止生成"只是 `AbortController` 断开 SSE 连接；后端 producer 有意"不随断开取消"
  （为 `/stream` 断线续传，轮次仍跑完落库）。这带来三个错乱：
  1. **并发交错**：停止后用户立刻再发一条，两个 producer 并发操作同一 session。后轮可能在前轮的
     assistant 消息落库前就 `load_messages`，导致 `agent_message` 行交错（user1,user2,asst2,asst1）、
     工具消息跨轮次配对，历史顺序永久错乱。
  2. **孤儿会话**：新会话行原先在请求入口 `chat()` 立即创建；若请求极早断开（producer 尚未运行），
     会留下一条没有任何消息的空会话。
  3. **前端假状态**：中断后助手气泡停在截断文本、工具卡片永久"执行中"转圈；若在 `turn_start`
     到达前断开，前端拿不到 sessionId，侧边栏不显示该会话。
- **修复**：
  1. 后端按 `session_id` 加互斥锁，producer 在锁内跑 `run_turn`，
     同一会话轮次串行：后轮等前轮落库完毕才载入历史。**注意锁实例的回收竞态**：
     初版用 `locks.setdefault(sid, Lock())` + finally `if not lk.locked(): locks.pop(sid)`，
     但"持有者释放锁"与"等待者被唤醒获取锁"之间有一个 `locked()==False` 的窗口，此时 pop 会删掉锁；
     后到者 setdefault 另建一把新锁，与仍持有旧锁的等待者并发 → 互斥失效。改为 `TurnLockRegistry`
     引用计数：进入者在 await 前同步 `refs++`，等待者也已计数，故只有 refs 归零且锁空闲才回收。
  2. 会话行创建延后到 producer 内、锁内执行（`ChatSessionStore.create(..., session_id=预生成)`）；
     producer 不随断开取消，故"建会话+跑轮次"必定完成，消除孤儿会话窗口。
  3. 前端 abort 后：气泡标记 `stopped`（显示"已停止生成"），仍在 running 的工具卡片标记为
     `stopped`（⏸ 灰色，不再转圈）；`finally` 中统一 `refreshSessions()` 补回后端建好的会话。
- **教训**："任务不随连接取消"是可靠投递的优点，但必须配套 ① 同资源并发串行化（锁），
  否则重叠任务互相踩踏；② 副作用（建会话/落库）放到必定执行的 producer 内而非可能早断的请求入口；
  ③ 前端中断是本地 UI 行为，要显式收尾所有"进行中"视觉状态，不能让其无限 pending。
